# GitHub 开源项目搜索助手

## 用途

从用户自然语言需求出发，经过需求挖掘、检索词拆解、GitHub 检索、过滤分类、深度解读，最终产出结构化推荐结果。

目标不是"给很多链接"，而是"给用户可理解、可比较、可决策、可直接行动的候选仓库列表"。

## 适用范围（V2.1）

- 数据源：GitHub 公开仓库 + Exa.ai 语义搜索（双通道）。
- 默认不授权（不使用用户 Token）。
- 默认硬过滤：`stars >= 100`、`archived=false`、`is:public`。
- 默认输出：单榜单（Top N），榜单内按"仓库归属类型"标注。
- 本流程默认不包含安装与落地实施（除非用户单独提出）。

### 配额说明（必须知晓）

**GitHub API（未授权）：**
- Core API：`60 次/小时`。
- Search API：`10 次/分钟`（独立于 Core 额度）。

**Exa.ai（免费层）：**
- 搜索：`1,000 次/月`。
- 内容抓取：按页计费。
- 特点：语义检索（embedding-based），自然语言查询，返回结构化内容。

- 需要在报告中注明检索时间与配额状态，避免结果不可复现。

## 工作流程

### 环节一：需求收敛（必须完成，不可跳过）

> **硬性门控**：环节一是整个流程的前置条件。无论用户的需求描述多么清晰，都必须走完本环节并获得用户明确确认后，才能进入环节二。禁止根据用户的初始描述直接推断需求并开始检索。即使用户说"直接搜就行"，也要先输出需求摘要让用户确认。

#### 第一步：需求挖掘与对齐

**目标**：把"我想看看 XX"转成可执行、可排序、可解释的检索目标。

**需确认信息（最少）**：

1. 主题（如：agent 记忆、RAG、浏览器自动化）
2. 数量（Top 10 / Top 20）
3. 最低 stars（默认 100）
4. 排序模式（必须二选一）：`相关性优先` / `星标优先`（默认：相关性优先）
5. 目标形态（必须二选一或多选）：
   `可直接使用的产品` / `可二次开发的框架` / `资料清单/方法论`

**建议补充信息（可选）**：

1. 偏好技术栈（Python/TS/Go 等）
2. 使用场景（学习、生产、对标）
3. 排除项（教程仓库、归档仓库、纯论文复现等）
4. 部署偏好（本地优先/云端优先/混合）

**阶段输出（固定格式）**：

```text
核心诉求：
- 主题：xxx
- 数量：Top N
- 最低 stars：>= 100
- 排序模式：相关性优先 / 星标优先（默认：相关性优先）
- 目标形态：xxx
- 偏好：xxx（可空）
- 排除：xxx（可空）
```

向用户确认以上信息。**用户明确确认后才能进入环节二，否则停在这里继续对齐。**

---

### 环节二：检索执行（以下环节由模型自主执行，无需用户介入，直到环节四交付报告）

#### 第二步：LLM 查询扩展 + 检索词拆解（8-15 组）

**目标**：通过 LLM 语义扩展，突破关键词匹配的局限，覆盖用户未明确表达的检索角度。

**阶段 A：LLM 查询扩展（自动执行）**

将用户需求描述交给 LLM（当前会话模型），要求从以下维度生成扩展查询：

1. **核心语义**：用户原话的直接转述（2-3 组）
2. **同义替换**：同一概念的不同表达方式（2-3 组）
3. **场景展开**：具体使用场景的描述（2-3 组）
4. **技术映射**：对应的技术术语、库名、协议名（2-3 组）
5. **跨界联想**：相邻领域中可能包含所需能力的项目（1-2 组）

LLM 扩展的查询用于 **Exa.ai 语义搜索**（自然语言友好）。

**阶段 B：GitHub 检索词拆解（人工规则）**

将扩展后的查询映射为 GitHub Search API 可用的关键词组合：

每组 query 由以下维度组合：

1. 核心词：用户目标词
2. 同义词：替代表达（如 long-term memory / stateful memory）
3. 场景词：coding、mcp、tool、platform、awesome、curated
4. 技术词：agent、sdk、framework、database、os
5. 排除思路：不在 query 里硬写过多负例，放到后续过滤阶段

**产出格式**：

```text
=== Exa.ai 语义查询 ===
Q1: "xxx" — 核心语义
Q2: "xxx" — 同义替换
Q3: "xxx" — 场景展开
...

=== GitHub 关键词查询 ===
G1: "xxx" — 目的说明
G2: "xxx" — 目的说明
...
```

#### 第三步：双通道检索与候选召回

**通道 A：GitHub Search API**（关键词检索）

1. 每组 GitHub query 执行检索（建议每组 30-50 条）。
2. 合并结果形成候选池。
3. 按 `owner/repo` 去重。

**通道 B：Exa.ai 语义搜索**（语义检索）

1. 使用 LLM 扩展的自然语言查询执行 Exa 搜索。
2. 每组查询取 Top 20 结果。
3. Exa 返回的是网页/仓库页面，提取其中的 GitHub 仓库链接。
4. 对于没有直接 GitHub 链接的结果，通过 `Contents API` 抓取页面提取仓库信息。

**双通道合并**：

1. 两个通道的结果合并为统一候选池。
2. 按 `owner/repo` 去重。
3. 标记来源通道（`github` / `exa` / `both`）——出现在双通道中的仓库天然具有更高可信度。
4. 记录检索时间与各通道 API 额度信息。

**候选池字段（最少）**：

1. `owner/repo`
2. `stars`
3. `description`
4. `repo_url`
5. `archived`
6. `language`
7. `updated_at`
8. `topics`
9. `license`
10. `source_channel`：`github` / `exa` / `both`

#### 第四步：去重与硬过滤

**硬过滤（默认）**：

1. `stars >= 100`
2. `archived = false`
3. `is:public`

**可选硬过滤（按需）**：

1. `fork = false`
2. 指定语言：`language:xxx`
3. 更新时效：最近 6-12 个月

**硬过滤执行规则**：

用户确认后的硬过滤条件是 Top N 主榜资格条件，不能在精排阶段被相关性、语义匹配度、双通道命中或 README 深读结果覆盖。

如果发现未满足硬过滤但高度相关的项目，不要丢弃；将其放入"低 star 但高价值项目 / 潜力项目"单独区域，并说明：

1. 为什么值得关注
2. 未进入主榜的具体原因
3. 对用户的实际价值与性价比：它解决了什么主榜项目没解决的问题，试用/调研成本高不高，是否值得用户额外花时间看

---

### 环节三：质量精炼

#### 第五步：噪音剔除与二阶段重排

**目标**：解决"命中 memory 但其实不是 agent memory"的噪音问题。

**噪音剔除规则（示例）**：

1. 与主题无关的通用工程仓库（即使 stars 很高）
2. 关键词误命中仓库（仅描述中偶然出现 memory/agent）
3. 无实质内容或异常仓库

**二阶段重排（借鉴 DeepGit 的双阶段检索思路）**：

**阶段一：元数据粗排**（快速筛选，不消耗额外 API）

基于已有元数据（stars、description、topics、language、updated_at、source_channel）对候选池打分：

1. 需求相关性（基于 description 和 topics 的关键词匹配）：30%
2. 场景适用性（目标形态匹配度）：25%
3. 双通道加分（同时出现在 GitHub 和 Exa 结果中的仓库 +10%）：10%
4. 活跃度（更新时效）：15%
5. 工程成熟度（stars 作为门槛后的参考信号）：10%
6. 语言/技术栈匹配：10%

从粗排中取 Top 15-20 进入精排。

**阶段二：README 语义精排**（LLM 深度阅读）

对粗排 Top 15-20 的仓库，使用 `WebFetch` 工具读取其 GitHub README 页面，提取：

1. 项目定位段（它是什么、解决什么问题）
2. 功能列表或架构描述
3. 快速开始/示例代码
4. 近期维护信号

将提取内容交给 LLM，以用户原始需求为锚点，进行语义相关性判断：

- **高度相关**：项目核心功能直接匹配用户需求（优先选入 Top N）
- **部分相关**：项目包含所需能力但不是核心功能（可选入）
- **弱相关**：项目方向不同但有参考价值（降权或剔除）
- **不相关**：关键词误命中（剔除）

精排产出最终 Top N 排序。

**Exa.ai Highlights 辅助**：对于 Exa 通道发现的仓库，可使用 Exa 的 Highlights API 快速提取页面关键片段（比全量抓取更省 token），辅助 LLM 判断相关性。

#### 第六步：仓库归属类型分类（必须）

**目标**：让用户一眼看懂"这个仓库到底是什么角色"，避免把框架、应用、目录混为一谈。

**推荐类型字典**：

1. 通用框架层
2. 应用产品层（可直接使用）
3. 记忆层/上下文基础设施
4. MCP 服务层
5. 目录清单层（awesome/curated）
6. 垂直场景方案层
7. 方法论/研究层

#### 第七步：深读与项目介绍撰写（必须）

**目标**：不是"仓库简介复述"，而是输出"对用户有决策价值"的详细介绍。

**深读最低要求**：

每个入选仓库至少查看：

1. README 核心定位段
2. 快速开始/功能章节标题
3. 近期维护信号（更新时间、Issue/PR 活跃）

**项目介绍写作要求（固定）**：

"项目介绍"必须包含两部分并写细：

1. 这是什么：它在系统架构中的角色和边界
2. 为什么推荐：它在用户当前目标下的价值（不是泛泛优点）

可补充：

1. 典型适用场景（1-2 条）
2. 限制或不适用场景（1 条）

---

### 环节四：交付与迭代

#### 第八步：单榜生成与报告交付（最终）

**交付结构（固定）**：

1. 需求摘要
2. 检索词清单（Exa 语义查询 + GitHub 关键词查询，各组 + 目的）
3. 筛选与重排规则（明确写出，含二阶段重排说明）
4. 结果总览（原始召回/去重后/过滤后，含双通道分布）
5. Top N 单榜（表格）
6. 低 star 但高价值项目 / 潜力项目（仅当存在未满足硬过滤但高度相关的项目时输出）
7. 结论与下一步建议

**Top N 表格字段（固定）**：

| 仓库 | 星标 | 仓库归属类型 | 项目介绍（是什么 + 推荐理由） | 其它信息补充 | 链接 |
|---|---:|---|---|---|---|

**"其它信息补充"建议内容**：

- 语言 / License / 最近更新时间
- 上手复杂度（低/中/高）
- 风险提示（若有）

#### 第九步：用户确认与迭代（可选）

**迭代触发条件**：

用户反馈"太泛/太窄/不够准/解释不够细"。

**迭代动作**：

1. 调整检索词（增加场景词或同义词）
2. 调整 stars 门槛（100 -> 200/500）
3. 增加限定（语言/方向/更新时间）
4. 调整类型权重（例如优先应用层或优先框架层）

## 默认参数（V2.1）

1. 最低 stars：`100`
2. 默认输出：`Top 10`
3. 默认过滤：`archived=false`
4. 默认必须分类：是
5. 默认项目介绍粒度：详细（至少"是什么 + 为什么推荐"）
6. 默认启用 Exa.ai 语义搜索通道
7. 默认启用 LLM 查询扩展
8. 默认启用二阶段重排（粗排 Top 15-20 → 精排 Top N）
9. 粗排取 Top 15-20 进入 README 精排

## 质量检查清单（交付前自检）

1. 是否完成需求对齐并明确"目标形态"
2. 是否有 LLM 扩展的语义查询（Exa 通道）+ 关键词查询（GitHub 通道）
3. 是否执行了双通道检索（GitHub + Exa.ai）
4. 是否记录了检索时间与各通道配额状态
5. 是否执行了去重、硬过滤和噪音剔除
6. 是否完成二阶段重排（元数据粗排 + README 语义精排）
7. 是否完成仓库归属类型分类
8. 是否每个推荐都有详细项目介绍（不是一句话）
9. 是否使用固定表格字段交付
10. 是否避免把安装实施混入本流程
